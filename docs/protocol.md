# Протокол umbrawg-tunnel

Дополнительный слой поверх датапаса AmneziaWG/WireGuard: FEC, канал
обратной связи и управление скоростью. Описан так, чтобы его можно было
воспроизвести независимо от этой реализации.

## 1. Модель совместимости

- Внешний транспорт — UDP, формат пакетов WireGuard/AmneziaWG не меняется.
- Слой включается только явной настройкой обеих сторон. Пока он выключен,
  байты на проводе идентичны AmneziaWG.
- Все служебные сообщения едут **внутри обычных data-сообщений** (тип H4),
  поэтому для наблюдателя они неотличимы от пользовательского трафика:
  те же заголовки, тот же header protection, тот же padding и трейлеры.
- Версия слоя не согласуется в handshake (формат handshake — WireGuard).
  Несовпадение настроек проявляется как потеря служебных пакетов;
  неизвестные виды служебных сообщений молча игнорируются.

## 2. Кадрирование

Внешнее data-сообщение (как в AmneziaWG):

```
+--------+--------+--------+--------+-------------------------------+
| type   | key_idx| counter| ciphertext (ChaCha20-Poly1305)        |
| u32    | u32    | u64    | ...                                   |
+--------+--------+--------+-------------------------------+
  4 байта  4 байта  8 байт
```

`type` — обфусцированный (header protection) тип из диапазона H4.

Расшифрованное содержимое — либо пакет внутренней сети, либо служебное
сообщение:

```
0x00            — маркер служебного сообщения (не является версией IP:
                   у IPv4 первый байт 0x4X, у IPv6 — 0x6X)
0x01..0xFF      — вид сообщения
```

Пустой payload по-прежнему означает keepalive. Пакет внутренней сети
начинается с 0x4X/0x6X и обрабатывается как раньше.

Виды служебных сообщений:

| Код  | Имя            | Назначение                                   |
|------|----------------|----------------------------------------------|
| 0x01 | FEC_REPAIR     | чётность группы пакетов                      |
| 0x02 | CC_FEEDBACK    | обратная связь для контроллера скорости      |
| 0x03 | CC_REQUEST     | запрос обратной связи с меткой времени       |

Все многобайтные поля — little-endian.

## 3. FEC

### 3.1. Параметры

- `fec_k` — сколько data-пакетов в группе (2..32, по умолчанию 10);
- `fec_m` — сколько ремонтных пакетов на группу (в схеме 0 допускается 1;
  поле оставлено для расширения);
- `fec_max_bytes` — верхняя граница размера восстанавливаемого пакета
  (по умолчанию 2048).

Защищаются только пакеты, несущие данные (внутренние IP-пакеты).
Служебные сообщения (FEC_REPAIR, CC_*) не защищаются: их потеря
компенсируется следующей обратной связью.

### 3.2. Формирование группы (отправитель)

Отправитель ведёт счётчик группы `block_id` (u16, циклический) и
накопитель. Для каждого отправленного data-пакета он запоминает:

- `counter` — значение поля counter внешнего сообщения (nonce);
- `len[i]` — полная длина внешнего data-сообщения (type+key_idx+counter+шифр);
- байты этого сообщения целиком.

Накопитель чётности:

```
parity[0..max_len) ^= payload_i[0..len_i)   (недостающие байты = 0)
max_len = max(len_i)
```

После `fec_k` пакетов отправитель шлёт один пакет FEC_REPAIR.

### 3.3. Формат FEC_REPAIR

```
смещение  размер        поле
0         1             0x00 (magic)
1         1             0x01 (kind)
2         1             scheme: 0 = XOR-чётность, 1..255 зарезервировано
3         1             flags: 0
4         2             block_id
6         1             k
7         1             m (в схеме 0 — 1)
8         8*k           counter[i] внешних data-сообщений группы
8+8k      2*k           len[i] — длина каждого защищённого сообщения
8+10k     1             max_len (в единицах 8 байт, округление вверх)
9+10k     max_len       parity: m блоков по max_len байт
```

`max_len` кодируется как `ceil(максимальная длина / 8)`, чтобы не вводить
u32; фактические байты чётности берутся из длины самого сообщения.

Ремонтный пакет шифруется и отправляется как обычное data-сообщение:
свой counter, свой padding, header protection, трейлеры и пейсер — то есть
внешне неотличим от данных.

### 3.4. Восстановление (приёмник)

Приёмник ведёт на каждого пира:

- битовое окно последних `W` значений counter (W = 4096) с номером
  поколения для обработки переполнения;
- кольцевой буфер копий содержимого последних `W` принятых data-сообщений
  (по умолчанию W = 64 записи), выделяется только при включении FEC.

При приёме data-сообщения отмечается counter и сохраняется копия
содержимого. При приёме FEC_REPAIR:

1. Для каждого `i` проверяется, есть ли `counter[i]` в окне.
2. Если потерян ровно один пакет и все остальные копии ещё в кольце —
   выполняется восстановление:

   ```
   payload_missing = parity ^ (XOR payload_i для всех принятых i)
   ```

3. Результат обрезается до `len[missing]` и вводится в обычный путь приёма
   как если бы пакет пришёл по сети (расшифровка, проверка replay-окна).
4. Если потеряно больше пакетов, чем `m`, или часть копий уже вытеснена —
   группа пропускается, потерь не добавляется.

Восстановленный пакет проходит те же проверки, что и принятый: подпись
Poly1305, индекс ключа, replay-окно. Подделка чётности не даёт доступа к
данным и отбрасывается этими проверками.

## 4. Обратная связь

### 4.1. CC_REQUEST (0x03)

Отправитель периодически (по умолчанию раз в 20 мс, параметр `cc_fb_ms`)
шлёт:

```
0   0x00
1   0x03
2   flags (0)
3   reserved (0)
4   timestamp: u64    — ktime_get_ns() в момент отправки
12  dropped: u64      — счётчик пакетов, отброшенных пейсером
```

`dropped` нужен, чтобы получатель вернул его обратно и отправитель мог вычесть
потери, которые возникли в **собственной** очереди пейсера, а не в канале.

CC_REQUEST/CC_FEEDBACK отправляются **вне пейсера**: иначе перегруженная
очередь задерживает обратную связь, RTT искажается, и контур самоудушается.
Пакеты по-прежнему проходят шифрование, padding, header protection и
обфускацию — наблюдатель не отличает их от данных.

### 4.2. CC_FEEDBACK (0x02)

Получатель отвечает на CC_REQUEST:

```
0   0x00
1   0x02
2   flags (0)
3   reserved (0)
4   echo_ts: u64          — timestamp из CC_REQUEST
12  recv_bytes: u64        — суммарно принято байт внешнего трафика
20  recv_packets: u64       — суммарно принято таких пакетов
28  reserved: u32 (0)
32  highest_counter: u64    — максимальный принятый counter (nonce)
40  echo_drops: u64         — dropped из CC_REQUEST, возвращается как есть
```

### 4.3. Измерения на отправителе

- `RTT = now - echo_ts` по каждому ответу;
- `delivery_rate = Δrecv_bytes / Δt` по **самому свежему** интервалу не короче
  10 мс; результат кладётся в слоты по 250 мс, берётся максимум по 8 слотам
  (окно 2 с);
- поверх короткого окна — **пиковое окно 10 с**: оценка не опускается ниже
  максимума за последние 10 с. Это принципиально: если внутри туннеля TCP,
  он сам является контроллером перегрузки, и его кратковременный откат после
  потери выглядит как падение полосы, хотя канал не менялся;
- `min_rtt` — минимум RTT за окно 10 с;
- **потери** считаются по разности nonce, а не по счётчикам, снятым в разные
  моменты:

  ```
  d_highest = Δhighest_counter     — сколько наших пакетов получатель увидел
  d_drop    = Δecho_drops          — сколько из них мы не отправили вообще
  sent      = d_highest - d_drop
  acked     = min(Δrecv_packets, sent)
  lost      = sent - acked
  ```

  Оба счётчика охватывают один и тот же набор пакетов, поэтому нет фантомных
  потерь от задержки обратной связи (при 400 тыс. пакетов/с сравнение голых
  счётчиков давало до 80 % «потерь»).
- доставка и потери ведутся по внешним пакетам, поэтому контроллер работает
  для любого внутреннего протокола: TCP, UDP, ICMP.

## 5. Контроллеры скорости

Пейсер общий для всех режимов: token bucket + fq-очередь на 8 бакетов по
хешу внутреннего 5-tuple, round-robin, всплеск 10 мс. Очередь ограничена
**~3 мс данных** (`128…4096` пакетов), а не фиксированным числом: глубокая
очередь превращается в bufferbloat, раздувает RTT внутреннего транспорта и
заставляет его сдаваться задолго до заполнения канала.

### 5.1. `brutal`

Фиксированный шейпер с **компенсацией потерь**, как в Hysteria 2.

- задаётся хорошая полоса `base` (Мбит/с);
- пейсер реально гонит `pace = base * 100 / ack_pct`;
- `ack_pct` — доля подтверждённых пакетов за последние 5 секунд (5 слотов по
  1 с, минимум 50 сэмплов, нижняя граница 80 %);
- при 5 % потерь пейсер сам поднимается до `base / 0.95`, и получатель
  видит заданную полосу.

Потери не режут скорость — это осознанное поведение: шейпер должен держать
заданную полосу на канале с потерями, а не «честно» сдаваться.

### 5.2. `bbr`

Адаптивный контроллер на измерениях из раздела 4.3, поведение повторяет
BBR из quic-go (Hysteria 2).

Параметр `cc_rate` задаёт **стартовую** скорость. Если он равен 0, старт
выводится из данных, а не из константы: `init_cwnd / min_rtt`, где
`init_cwnd = 32 * 1420` байт (как `initialCongestionWindow` в QUIC).

Фазы:

- **Startup.** `pacing = max(pacing, 2.885 * bw)`; пока замеров нет —
  геометрический разгон от стартовой скорости. Раунд — 100 мс (квант
  фильтра полосы, а не RTT: быстрее проверять рост бессмысленно). Выход в
  `Drain`, если три раунда подряд рост < 25 %, потери ≥ 2 %, либо прошло
  10 с.
- **Drain.** `pacing = 0.347 * bw` (то есть `bw / 2.885`); выход, когда
  очередь пейсера пуста или прошло `max(2 * RTT, 20 мс)`.
- **ProbeBW.** `pacing = bw * gain`, цикл gains =
  `[1.25, 0.75, 1, 1, 1, 1, 1, 1]`, фаза не короче 100 мс. При потерях ≥ 2 %
  усиливающие фазы заменяются на 1.0.
- **ProbeRTT.** Каждые 10 с без нового `min_rtt` на 200 мс `pacing = bw`.

Особенности реализации, без которых контроллер не работает:

- при простое (`sent_bytes` не менялся и очередь пуста) тик ничего не
  делает: иначе startup «выгорал» за время настройки интерфейса, а drain
  делил скорость пополам на каждом тике;
- после паузы > 200 мс раунд перезапускается, состояние фаз сохраняется;
- ограничения: `pacing ∈ [64 кбит/с, 100 Гбит/с]`; при отсутствии обратной
  связи дольше 2 с скорость не увеличивается.

Внутри туннеля может быть и TCP, и UDP: обратная связь строится по внешним
пакетам, а не по разбору внутренних ACK. Но если внутри TCP, он сам является
контроллером перегрузки: дропы в пейсере заставляют его сжимать окно, и
пиковое окно 10 с нужно именно для того, чтобы BBR не принял это за сужение
канала. Для TCP внутри обычно выгоднее `brutal` с известной полосой.

## 6. Взаимодействие с обфускацией

Обфускация AmneziaWG (H1..H4, S1..S4, content padding, junk I1..I5,
random trailers, header protection) применяется к служебным сообщениям
ровно так же, как к data-пакетам:

- тип всегда из диапазона H4;
- header protection пересчитывается по первым 12 байтам (у служебных
  сообщений это magic+kind+...);
- padding и трейлеры задаются теми же правилами;
- FEC_REPAIR идёт через пейсер (это часть потока данных), а CC_REQUEST и
  CC_FEEDBACK — вне пейсера, но с теми же правилами шифрования, padding и
  обфускации.

Дополнительно: CC_* получают штатный padding устройства (transport padding,
content padding, random trailers), поэтому их размер не выделяет их среди
data-пакетов.

## 7. Параметры и значения по умолчанию

| Параметр        | По умолчанию | Диапазон        |
|-----------------|--------------|-----------------|
| `cc`            | none         | none/brutal/bbr |
| `cc_rate`       | 0            | 0..1e11 бит/с   |
| `fec_k`         | 0 (выкл.)    | 0, 2..32        |
| `fec_m`         | 0 (выкл.)    | 0, 1 (схема 0)  |
| `cc_burst_ms`   | 10           | 1..100          |
| `cc_fb_ms`      | 20           | 5..1000         |

Конфигурация задаётся на пира и симметрична: FEC и контроллер должны быть
включены на обеих сторонах.

## 8. Ограничения и безопасность

- Очередь FEC на приёмнике ограничена (`W` записей); при переполнении
  новые группы не восстанавливаются.
- Служебные сообщения не создают новых состояний аутентификации: всё
  внутри обычного шифрованного data-сообщения.
- Восстановленный пакет обязан пройти Poly1305 и replay-окно; иначе он
  отбрасывается.
- FEC не защищает handshake; потеря handshake-пакетов обрабатывается
  штатными таймерами WireGuard.
